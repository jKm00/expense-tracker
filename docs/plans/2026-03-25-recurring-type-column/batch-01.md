### Step 2: Generate the Drizzle migration

Run:

```bash
npm run db:generate
```

Expected: Drizzle-kit generates a new migration folder under `drizzle/` with a `migration.sql` file.

### Step 3: Verify the migration SQL

Open the generated `migration.sql`. It should contain SQL similar to:

```sql
ALTER TABLE "recurring_product" ADD COLUMN "type" "transaction_type" DEFAULT 'expense' NOT NULL;
```

> **Note:** The `transaction_type` enum already exists in the database (created by the transactions migration). Drizzle-kit should NOT generate a `CREATE TYPE` statement. If it does, the migration is wrong — remove the `CREATE TYPE` line since the enum already exists.

> **Migration safety:** On PostgreSQL 11+, `ALTER TABLE ... ADD COLUMN ... DEFAULT constant NOT NULL` is an instant metadata-only operation (no table rewrite). This is safe for tables of any size.

### Step 4: Run the migration

```bash
npm run db:migrate
```

Expected: Migration applies successfully. No errors.

> **Data flow verification:** The `type` field is guaranteed to persist end-to-end because:
> 1. Controller schemas (`NewRecurringProductSchema` / `UpdateRecurringProductSchema`) validate `type` via `createServerFn(...).inputValidator(...)` — requests without `type` are rejected
> 2. The handler passes `data` (including `type`) to `recurringService` which passes it to `recurringRepo`
> 3. `recurringRepo.save()` calls `db.insert(recurringProduct).values(data)` — Drizzle infers columns from the schema, so `type` is included
> 4. `recurringRepo.update()` calls `db.update(recurringProduct).set({...data, updatedAt: new Date()})` — same mechanism
> 5. Read queries use `select({ recurringProduct, product })` which returns ALL columns — `type` is returned automatically

> **Note:** After this task, the `recurring.mutations.ts` file does NOT need changes — it uses the `NewRecurringProductDTO` and `UpdateReucrringProductDTO` types which are inferred from the controller schemas, so they automatically pick up the new `type` field.
